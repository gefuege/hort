<>Hort

Threat model

As of November 2026 · Privacy (Datenschutz) · Terms

This page says what Hort protects and what it does not. It describes Hort 1.0 as built; where the code and a promise differ, the code wins.

What Hort protects

  • The server holds ciphertext only. Secret names, descriptions and values are encrypted on your device before they are sent. The server cannot decrypt them, and it cannot forge or change a revision, move one to another account, or replay an old passphrase slot (slots carry a signature by your account key and a version).
  • Two secrets are needed to open your data: passphrase plus Secret Key. The Secret Key is 128 bits and never leaves your devices. Someone who gets the passphrase slot from the server (it can be fetched without signing in, which is how the Emergency Kit works) still cannot brute-force the passphrase without the Secret Key. The passphrase is stretched with Argon2id.
  • Passkeys are bound to hort.pm. A phishing page on another domain cannot use them. Passkeys that support the PRF extension can unlock the vault in the browser without passphrase and Secret Key.
  • The vault key stays in the browser. The web app keeps it in memory. To survive a reload within the lock time you picked (default 1 hour of idle time), it stores the vault key in the browser encrypted with a per-session unlock key that only the server hands out, only to your signed-in session, for that session. Neither the server alone nor the browser storage alone can open it. Signing out, choosing "immediately" or an ended session deletes it.
  • Data placement: each account lives in its own SQLite Durable Object in Cloudflare's EU jurisdiction.
  • A stolen locked device gives the thief the encrypted vault file and the Secret Key file, but not the passphrase. Revoking the device ends its server access.
  • Agents: the MCP tool request_secret sends your agent's request to the web app, where you enter the value. The value never enters the chat. It adds no read power, because an agent with shell access could already run hort get.

What Hort does not protect against

  • A compromised device while the vault is unlocked. Malware, or anyone using the unlocked machine, can read and write everything, including the session file the CLI keeps while unlocked.
  • Malicious web code served by the operator. If hort.pm, or Cloudflare, served you modified JavaScript, that code could read your passphrase, Secret Key and every value in the browser session. Users who only use the CLI are not affected. This is the largest residual risk of the web app. Mitigations: a strict Content Security Policy, no third-party code, open source. Checking the code that was actually served is on you; if you cannot accept this, use the CLI only or self-host.
  • A compromised vault key. Whoever holds your vault key (a stolen unlocked device, a leaked session file, malicious web code) can read everything, derive your account key and enroll new devices and passkeys, including after being revoked. Revoking a device does not help. In Hort 1.0 the only recovery is a new account: run hort init on a clean device, set your values again and rotate the exposed secrets at their source. Hort 1.0 has no vault key rotation.
  • Withholding and rollback. The operator can deny service, delay revisions or refuse enrollment. Hort 1.0 cannot detect that new revisions are being held back. Every device keeps a full copy, so the server never holds the only one.
  • Metadata the server sees (the list below).
  • Lost passphrase or Secret Key. There is no reset and no backdoor (see Recovery).

What the server can see

The server can see:

  • your account ID (random, no name or e-mail) and its creation time;
  • device names (you choose them with --name; the default is generic, such as darwin-ab3d), device and passkey public keys, and their created, last-seen and revoked times;
  • number, size, order and arrival time of revisions, and which device pushed each one;
  • that an agent request exists, its status, time and encrypted size;
  • session timing, and IP addresses and request details as processed by Cloudflare (see Privacy).

The server cannot see secret names, descriptions, fields, environments, values, your passphrase, Secret Key or vault key, nor what a revision contains (a set, a delete or a description), nor the name of a requested secret.

From sizes and times the operator can infer roughly how much you store and when you use Hort. Hort 1.0 adds no padding.

Recovery

  • Forgot the passphrase but a device is unlocked, or a passkey unlocks the web app: set a new one (hort passphrase, or in the web app under Access).
  • Lost the Secret Key but a device is unlocked: hort kit prints it again.
  • Lost a locked device: hort devices revoke <id>. A thief still needs the passphrase to read a copied vault file.
  • Lost both passphrase and Secret Key, with no unlocked device or passkey: the data cannot be recovered. Hort cannot help, by design.
  • Vault key compromised: new account and rotation at the source, as above. hort help recovery says the same.

Keep the Emergency Kit (Secret Key and account ID) apart from your passphrase. Whoever holds both can read everything.

You can also run your own server: see self-hosting. That moves the operator role to you; it does not remove the trust in the code your server serves.
